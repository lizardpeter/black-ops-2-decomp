# Store checksum reconstruction

The primary target is t6mp_msstore (x64), not the x86 dedicated server.
The original PC server source unit is named by its PDB and exported in
analysis/CoDMPServer_PC/pseudocode/live/live_anticheat.cpp.c. The Store MP
pseudocode and disassembly contain both CRC recurrence loops inlined
into the hash continuation body, and show hash initialization and
finalization logic. Do not assign fictitious standalone Store entries
to inlined functions.

## Authored code and scope

src/live/live_anticheat.cpp contains the CRC arithmetic and a bounded,
caller-owned buffer model of the CRC lifecycle. The record layout
matches the observed 32-byte Store MP context accesses and has
compile-time size and offset checks. Allocation, incremental processing,
completion and slot reuse are represented. The model uses buffer offsets,
rejects unsupported modes and invalid ranges, and rejects premature
completion. These are deliberate offline API constraints, not claims
about the original ABI or all its edge cases. No remote challenge
processing or runtime override is implemented.

instruction listing passed 216 differential cases (360 original

generated reflected CRC32 table; the original table bytes were not
available. Thus this is evidence for valid-input continuation behavior,
not complete binary parity, not a Windows build, and not validation
of startup, finalization or network/service logic.

SP and ZM have PE/unwind inventories only in the current repository,
without comparable full disassembly. No shared-code parity claim is
made. Fetching the Store executable from the configured R2 host failed
with a DNS error in the execution environment.

No generated analysis, runtime hooks, or function-status claims
were changed.

## Original Store PE verification (2026-11-26, supersedes transfer limitations above)

All three original x64 PE images were obtained from encrypted handoff
run 45860949016, artifact 15138322094. Their SHA-256 hashes were
independently recomputed locally and match target.toml. The read-only
test `tests/verify_store_crc_tables.py` confirms that each image contains
one complete, byte-identical copy of the 256-entry reflected CRC32
table generated by the authored source.

Reproduce the table check using local original files:

```sh
python tests/verify_store_crc_tables.py /path/to/local/store/executables
```

The MP and ZM startup and continuation bodies are identical when only
their relative data-reference displacements are normalized. The MP
continuation bytes also exactly match the previously exported Ghidra
instruction listing. For both MP and ZM, the two CRC recurrences are
inlined into the continuation body. SP has the same CRC table, but no
identical standalone startup or continuation body was established;
this does not imply that those behaviors are absent in SP.

Isolated Linux x86-64 original-instruction replay, using the extracted
original CRC table for each build, a private context pool and owned

All comparisons passed. Startup tests cover allocation, record bytes,

## Original-style authored lifecycle (2026-11-26, supersedes offline source layout)

The bounded buffer model has moved to `tests/live_checksum_model.h`.
`src/live/live_anticheat.cpp` now contains the recovered Store-target
source functions with the original reference signatures: both CRC
helpers, StartHash, ContinueHash and CompleteHash. The last three
are compiled for T6_STORE. HashInfo is defined in the corresponding
production header, with all seven offsets and its 32-byte size
checked at compile time.

The authored lifecycle preserves the observed Store MP/ZM semantics,
including the accepted but non-computing mode 2, fixed Store chunk
size, first-free-slot allocation, original 32-bit address field and
record clearing even on early completion. This is a native source
reconstruction, not a remote challenge implementation. CompleteHash
uses the reference prototype and observed inlined finalization
behavior, not a claimed standalone Store entry. Mode 2 is not a
reconstructed SHA algorithm. No live integrity service or runtime
hook is installed; native pool storage has not been bound to the
original hybrid-build global. SP equivalence remains unresolved.

buffers only; optional original replay fixtures are generated locally):

## Finalization verification and service boundary (2026-11-26)

The three original PE hashes were independently rechecked. An identical
inlined CRC finalization instruction fragment occurs once in each of
MP and ZM, and has no exact match in SP. This is a byte-pattern finding,
not proof of the absence of equivalent SP behavior.

A local isolated replay of the original MP and ZM finalization
fragments, using synthetic contexts and no original service or game
process, passed 450 CRC comparisons per build (900 total). Output,
return success and all 32 cleared context bytes were compared with
the authored helper. Cases include early completion, boundary lengths,
multiple seed values and both CRC modes. Non-CRC caller observations
(225 per build) establish that the inlined caller's output behavior
is not equivalent to the standalone helper's non-CRC output contract.
Those observations are not counted as differential passes or as a
reconstructed SHA implementation. No equivalence is asserted for
unspecified non-CRC caller output.

The original fragment replay was local only; no extracted original
code or service-facing replay fixture is committed. The new portable
native regression in tests/live_checksum_finalization_test.cpp passed
450 CRC and 225 standalone non-CRC cases, including slot reuse,
with both optimized compilation and ASan/UBSan on Linux x86-64.

```sh
g++ -std=c++17 -O2 -Wall -Wextra -Werror -DT6_STORE -Iinclude src/live/live_anticheat.cpp tests/live_checksum_finalization_test.cpp -o /tmp/t6-finalization-test
/tmp/t6-finalization-test
```

At subsystem level, the existing generated MP match inventory identifies
candidate challenge deserialization, response serialization, submission,
and completion handling in the Demonware and live layers. The evidence
is string, registration, and call-graph matching (confidence 0.75-0.89),
not proof of their complete signatures or online behavior. CRC helper
validation must not be interpreted as validation of the service protocol,
authenticity, server acceptance, or the complete challenge lifecycle.
No remote endpoint was contacted; no service-facing implementation,
runtime binding or integrity behavior changed.

All three builds contain the same CRC table; SP has no exact normalized
MP startup or continuation match and no identical inlined finalization
fragment. SP function-level equivalence remains unresolved.
