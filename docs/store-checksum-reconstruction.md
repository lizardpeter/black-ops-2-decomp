# Store checksum reconstruction

The primary target is t6mp_msstore (x64), not the x86 dedicated server.
The original PC server source unit is named by its PDB and exported in
analysis/CoDMPServer_PC/pseudocode/live/live_anticheat.cpp.c. The Store MP
pseudocode and disassembly contain both CRC recurrence loops inlined
into the hash continuation body, and show hash initialization and
finalization logic. Do not assign fictitious standalone Store entries
to inlined functions.

## Authored code and scope

src/live/live_anticheat.cpp contains the CRC arithmetic and a bounded,
caller-owned buffer model of the CRC lifecycle. The record layout
matches the observed 32-byte Store MP context accesses and has
compile-time size and offset checks. Allocation, incremental processing,
completion and slot reuse are represented. The model uses buffer offsets,
rejects unsupported modes and invalid ranges, and rejects premature
completion. These are deliberate offline API constraints, not claims
about the original ABI or all its edge cases. No remote challenge
processing or runtime override is implemented.

## Verification

```sh
g++ -std=c++17 -O2 -Wall -Wextra -Werror -Iinclude src/live/live_anticheat.cpp tests/live_checksum_test.cpp -o /tmp/t6checksum-test
/tmp/t6checksum-test
```

Executed in Linux x86-64: 1,542 arithmetic cases and 216 lifecycle
cases passed, plus pool exhaustion/reuse, invalid bounds and standard
CRC test vector checks. A separate isolated replay of the 237-byte
Store MP continuation body extracted from the repository's Ghidra
instruction listing passed 216 differential cases (360 original
calls) over owned input buffers. The replay supplied an independently
generated reflected CRC32 table; the original table bytes were not
available. Thus this is evidence for valid-input continuation behavior,
not complete binary parity, not a Windows build, and not validation
of startup, finalization or network/service logic.

SP and ZM have PE/unwind inventories only in the current repository,
without comparable full disassembly. No shared-code parity claim is
made. Fetching the Store executable from the configured R2 host failed
with a DNS error in the execution environment.

No generated analysis, runtime hooks, or function-status claims
were changed.

## Additional offline pool regression (2026-11-26)

`tests/live_checksum_pool_test.cpp` exercises 32 rounds of 16
simultaneously active contexts against an independent bitwise CRC
reference, with deterministic generated buffer contents, lengths,
offsets and seeds. It also checks rejection of foreign handles,
short/null buffers, invalid progress, invalid block size and premature
completion, and verifies input preservation.

Build and execute locally:
```sh
g++ -std=c++17 -O2 -Wall -Wextra -Werror -Iinclude src/live/live_anticheat.cpp tests/live_checksum_pool_test.cpp -o /tmp/t6checksum-pool
/tmp/t6checksum-pool
```

Observed: 512 interleaved lifecycles and 2,127 continuation calls passed.
The same test and the initial regression also passed AddressSanitizer
and UndefinedBehaviorSanitizer (GCC, Linux x86-64, -O1 -g
-fsanitize=address,undefined -fno-omit-frame-pointer). These are
offline model tests, not original-binary differential counts.

The R2 runner's BO2 handoff workflow succeeded on November 24
(run 45422971734), but its one-day artifact is no longer listed.
The existing isolated MP replay passed again (216 cases, 360 calls).
No new original executable was obtained and SP/ZM parity remains
unverified. No live integrity behavior or runtime hooks changed.

## Original Store PE verification (2026-11-26, supersedes transfer limitations above)

All three original x64 PE images were obtained from encrypted handoff
run 45860949016, artifact 15138322094. Their SHA-256 hashes were
independently recomputed locally and match target.toml. The read-only
test `tests/verify_store_crc_tables.py` confirms that each image contains
one complete, byte-identical copy of the 256-entry reflected CRC32
table generated by the authored source.

Reproduce the table check using local original files:

```sh
python tests/verify_store_crc_tables.py /path/to/local/store/executables
```

The MP and ZM startup and continuation bodies are identical when only
their relative data-reference displacements are normalized. The MP
continuation bytes also exactly match the previously exported Ghidra
instruction listing. For both MP and ZM, the two CRC recurrences are
inlined into the continuation body. SP has the same CRC table, but no
identical standalone startup or continuation body was established;
this does not imply that those behaviors are absent in SP.

Isolated Linux x86-64 original-instruction replay, using the extracted
original CRC table for each build, a private context pool and owned
input buffers, with no game process or service:

| Build | Startup comparisons | Continuation cases | Continuation calls |
| --- | ---: | ---: | ---: |
| MP | 2176 | 1120 | 1680 |
| ZM | 2176 | 1120 | 1680 |
| Total | 4352 | 2240 | 3360 |

All comparisons passed. Startup tests cover allocation, record bytes,
pool exhaustion and allocation following local slot reset, for valid
CRC modes. Continuation tests compare completion state, progress,
CRC state, and unchanged context fields after each original call,
including empty and multi-block buffers, alignments and seed patterns.
The previous independent arithmetic and pool regressions were rerun
successfully (1542 arithmetic cases, 216 lifecycles, 512 interleaved
lifecycles and 2127 interleaved continuation calls).

The isolated machine-code replay was executed locally; its fixtures
are not committed. The portable PE table test is committed and
reproducible without third-party Python packages. The model is still a
bounded caller-owned buffer API, not a complete native live integrity
implementation. Original finalization, SP code parity and the Windows
integration build have not been differentially validated. No remote
challenge logic or runtime integrity hooks were changed.
